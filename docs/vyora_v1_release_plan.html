2. Root Cause Analysis: Why Were Changes Done Piecemeal?

The Core Problem Identified by Leadership: "Currently we update things in one place only; if the same thing is used in another module we need to update that as well. For example, adding i18n languages took 3 to 4 prompts. Why wasn't that achieved in one shot?"

An honest architectural retrospective reveals three specific technical causes for this friction:

  1. Component Dispersion (Lack of a Shared Abstraction): Filter toolbars, search bars, and table headers were implemented individually inside module folders (e.g. InvoiceFilterToolbar, PartyFilterToolbar, ProductFilterToolbar) rather than consuming a unified polymorphic <TableToolbar> component. Local strings were hardcoded in local configs instead of binding to a global schema.
  2. Namespace Fragmentation in i18n Dictionaries: Status keys were scattered across multiple JSON files without clear naming conventions (e.g. invoices.json had filter.paid, common.json had status.paid, while ALL was unmapped). When one view was translated, the others retained unmapped keys.
  3. Absence of a Mandatory Whole-App Audit Step: AI agents previously operated with narrow "prompt-level myopia"—fixing only the screen mentioned in the user's prompt rather than grepping the codebase for all identical occurrences across Products, Invoices, Parties, Payments, Purchases, and Inventory.

3. The "One-Shot Whole-App" Engineering Standard (For Senior Dev & QA Agents)

To eliminate piecemeal edits permanently, every engineer and AI subagent must follow this non-negotiable architectural protocol:

Mandatory Invariant Rule: The Rule of Universal Application
Whenever a component pattern, UX rule, schema constraint, or translation key is modified, the developer agent MUST audit and apply the change across ALL 6 CORE DOMAINS before submitting code for QA sign-off:
1. Products • 2. Parties (Customers/Suppliers) • 3. Invoices • 4. Purchases • 5. Payments • 6. Inventory

Standard Architectural Rules

  • Shared Component Enforcement: All tables MUST use src/components/ui/Table.tsx and Pagination.tsx. All filter inputs MUST use SearchInput.tsx (with 300ms built-in debounce) and Select.tsx (Radix UI). Never write custom inline dropdowns or un-debounced inputs.
  • Universal i18n Contract:
    • All shared statuses (ALL, PAID, PENDING, OVERDUE, CANCELLED, ACTIVE, INACTIVE) MUST reside in common.json under status.*.
    • All standard actions (Create, Edit, Delete, Search, Filter, Reset, Cancel, Save) MUST reside in common.json under actions.*.
    • Whenever a new string is added, the agent MUST update en, hi, and gu simultaneously in the same file change. Zero hardcoded strings permitted.
  • Radix UI Safety Standard: Any dropdown or select component MUST use defensive, non-crashing components. SelectLabel is standardized as an accessible styled <div> to prevent Radix SelectGroup context errors.
  • Zero-Data Clean Slate Standard: When a table has 0 records and no active search/filters, all filter bars, search inputs, and pagination controls MUST be hidden, rendering only a focused <EmptyState> card with a primary creation CTA.
  • Sticky Modal Architecture: Every modal must use <Modal footer={...}> with full-bleed responsive buttons (full width on mobile, right-aligned on desktop). No floating dividers or nested scrollbars.

5. Phased Product Roadmap

Version 1.0 — Core Foundation & Release Gate (Current Scope Wrap-Up)

  • Scope: Complete daily-use billing for retail/wholesale trade. Auth, Tenant Isolation, Product Catalog, Party Directory, Sales Invoices (Draft & Finalize), Purchase Bills, Payment Vouchers (Receipt & Payment), Inventory Adjustments, Expenses, Dashboard, Core Reports.
  • Signature Polish: Tri-lingual i18n (EN/HI/GU), Theme B Light/Dark mode, accessible Radix Selects & DatePickers, debounced search, mobile companion sync, and SaaS checkout.

Version 2.0 — Operational Parity (Vyapar Equivalent Operations)

  • Document Flow Pipeline: Quotations / Estimates → 1-click conversion to Sales Invoices. Delivery Challans → 1-click billing.
  • Returns & Adjustments: Credit Notes (Sales Return) and Debit Notes (Purchase Return) with automated stock replenishment.
  • Banking Ledger: Bank Accounts & Cash In Hand ledgers; Contra vouchers; Dynamic UPI QR code printed directly on invoice PDFs.
  • Batch & Barcode: Batch numbers, expiry date tracking, and USB/camera barcode scanner input for lightning-fast billing.

Version 3.0 — Extended Compliance, Scale & Automation

  • Tax Portal Automation: GSTR-1 & GSTR-3B offline JSON exports; Direct E-Way Bill and E-Invoice (IRN) generation via GSP APIs.
  • Offline-First & Mobile Sync: SQLite / WatermelonDB client database with delta-sync architecture for unreliable internet.
  • Full Accounting: Journal vouchers, Trial Balance, Profit & Loss, and Balance Sheet verified by certified accountants.

8. Senior Developer Agent & QA Agent Handoff Protocol

To ensure flawless execution between autonomous AI coding agents, this strict operational workflow must be followed:

Senior Developer Agent Protocol:
  1. Atomic Vertical Slices: Implement fixes one domain at a time (UI + validation + API + tests). Do not make sweeping unverified refactors.
  2. Whole-App Rule: If fixing a UI pattern (e.g. icon button, modal footer, select dropdown), update all 6 modules in the same session.
  3. Satisfy Layers 1 to 4: Format (Prettier), Lint (ESLint), Typecheck (tsc --noEmit), and Tests (Vitest) must all pass before handoff.
  4. Build Verification: Always run npm run build in vyora-frontend and npm run build in vyora-backend before reporting completion. Zero TypeScript errors allowed.
  5. Strict Git Rule: NEVER execute git push. Only commit locally if requested.
QA Verification Agent Protocol:
  1. Tri-Lingual Language Sweep: Verify every page under English, Hindi, and Gujarati. Ensure table headers, filter buttons, badges, and modal titles change dynamically.
  2. Dark/Light Theme Contrast Check: Toggle Theme B dark and light mode; verify that text contrast on table rows, card surfaces, and inputs meets WCAG AA standards.
  3. Zero-Data & Error Boundary Audit: Verify clean empty states on empty tenants; ensure no Radix or React unhandled runtime exceptions occur.
  4. Automated Test Suite: Execute backend integration tests (npm run test) and verify 100% pass rate.
  5. Gatekeeper Certification: Validate Layer 5 pre-commit compliance before certifying release readiness.
